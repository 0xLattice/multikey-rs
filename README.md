# multikey-rs

Rust port of [0xLattice/Multikey](https://github.com/0xLattice/Multikey).
Independent local repository; not yet published to GitHub or crates.io.

Encodes and decodes Ed25519, secp256k1, P-256/384/521, and ML-DSA-44/65/87
public-key envelopes as unsigned-varint codec plus opaque key bytes. Hex accepts
uppercase digits and an optional lowercase `0x` prefix. Encoding is lowercase.
As in Swift, empty key bytes are permitted and cryptographic validity is the
caller's responsibility. Non-minimal varints of known codes remain accepted.

The compatibility decoder matches Swift's tenth-byte truncation and its
pairwise hex parsing (`+1` and `-0` are accepted as byte values). Applications
requiring stricter envelopes can explicitly use `decode_strict` or
`from_hex_strict`. Consensus callers must apply their source-level canonical
encoding checks separately: decoding an envelope is not signature admission.

```rust
use lattice_multikey::{KeyType, Multikey};
let key = Multikey { key_type: KeyType::Ed25519, key_bytes: vec![42; 32] };
assert_eq!(Multikey::decode(&key.encode()).unwrap(), key);
```

cargo test --locked

`upstream-lock.json` records the reference commit. Forty-eight checked-in vectors
were generated by compiling the unmodified Swift codec, covering every key type
and key lengths through 2,592 bytes. Regenerate them with a checkout at that commit:

```sh
python3 scripts/swift-fixtures.py /path/to/Multikey
```

An additional 297 actual Swift cases cover all 256 tenth-byte values,
continuation/truncation boundaries, signed hex pairs and malformed Unicode.
Regenerate with `python3.12 scripts/swift-malformed-fixtures.py ../Multikey`.
The corpus records the pinned source hashes and checks exact rejection classes.

## Reusing Rust multiformats

Encoding delegates to `unsigned-varint` 0.8. The compatibility decoder remains
local: standard decoding rejects nonminimal varints that the pinned Swift codec
accepts, and Swift also has specific signed-hex behavior. The existing 48 valid
and 297 malformed Swift observations continue to pass with the shared encoder.

`cryptidtech/multi-key` is not a wire-compatible replacement: its container adds a
Multikey sigil, comments and typed attributes, while this platform envelope is a
key-code varint followed by opaque bytes. See its
[encoding implementation](https://github.com/cryptidtech/multi-key/blob/f662991a7f623b9b8ec313b6ea4b0231c8b09ca0/src/mk.rs#L291-L338)
and the [standard decoder policy](https://github.com/paritytech/unsigned-varint/blob/10d55e5dbdd7f61b6495bd12a49d06df82e08612/src/decode.rs#L66-L85).
